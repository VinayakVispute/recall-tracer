Recall Tracer Build Plan

What Recall Tracer must be when we press Submit: one agent, one FalkorDB graph, from the first illness report to approved store notices in under an hour of a coordinator's time and under a minute of the agent's. This page describes the finished product, page by page, and the work that gets us there.

Everything on this page is written as the target state. The repo on main (commit a6fef2c) is the starting point, not the finish line; the build plan says what remains per item. Priorities: P0 is in the demo video, P1 strengthens the README and the live pitch, P2 is Track 2 and only after the video is recorded.

What we submit

A hosted web app, a repository with one-command Docker setup, a three-minute captioned video, and a README that quotes every Cypher query. The product, as a judge will experience it:

  1. Outbreak intake. Paste six illness reports. The agent walks each case backward through the graph and names the one ingredient lot that explains every case, with the decoys ruled out and the evidence path per case.
  2. Supplier notice. Open the incident on that lot with its hazard. A 24-hour regulatory clock starts and an Incident node is written to FalkorDB.
  3. Live trace. Seven agent steps stream in. The record network lights up hop by hop. Every step shows its tool, its Cypher, and FalkorDB's latency in milliseconds.
  4. Incident dashboard. Hazard class to confirm, headline numbers, what left the plant, where it went, exposure, public notice facts, and a decision for every store.
  5. Evidence for any store. One plain sentence and the chain of records that proves it, or the missing record, or the backward proof that the store is clear.
  6. Approval and export. Confirm the class, approve notices by state, download the FDA-format shipping CSV. Nothing is ever sent.
  7. Incident history. The graph remembers every incident; the next notice on the same supplier says so.

States the shell must handle

  • No incident open. Outbreak and Supplier notice tabs are active; Incident tab shows "No incident open" with a one-line explanation and the seeded example ready to run.
  • Running. Incident tab shows the live trace; the Open button is disabled; the progress bar in the header advances per step.
  • Decided, unconfirmed. Dashboard visible; notices queue disabled with the reason "Confirm the class first".
  • Confirmed. Approvals enabled; header shows who confirmed and when.
  • Reload. The last decision loads from the API without rerunning the agent; replay is offered.
  • Error. Bad lot code, unknown lot, unreachable FalkorDB, model declined: each is a sentence that says what to do next, shown where the user acted.

Pages and mockups

One mockup per page, drawn in the product's own look at desktop width. Each page lists what is on it, what the user can do, which API route feeds it, and what it must look like in its empty, running and finished states. Phone width stacks every two-column layout into one.

What the replay shows

  • The same record network as the live view, set to the state after any step: which records had been reached, held, flagged or cleared at that moment.
  • A timeline with one marker per agent step at its real timestamp. Amber markers are judgement steps, green the backward check. The filled track is what has played.
  • A caption under the track naming the current step, its result, its tool and its FalkorDB latency.
  • The log on the right scrolls to the current step and dims the others.

Interactions

  • Play, pause, restart, speed 0.5×, 1×, 2×. Arrow keys step; space plays.
  • Drag the playhead or click a marker to jump; the graph redraws instantly to that step's state.
  • The link carries the step as a plain anchor (#step-6) so a judge can open the exact moment.
  • Replay works without an API key from the recorded run; "Replay on" in the top bar says it is not live.

Where it is used

  • On the Incident tab after any finished run, and as the default for the demo video.
  • On the hosted app for judges, so the first thing they see moves.

Outbreak source finder

The feature that turns a recall tool into an investigation tool, and the clearest multi-hop reasoning in the project. It follows how FDA and CDC actually work a cluster: cases linked by whole genome sequencing, interviews that yield where and when people shopped, then a backward trace from each point of purchase to a common source.

Graph additions

ElementPropertiesMeaning
Cluster nodeid, pathogen, opened_atThe linked cluster the cases belong to. Page 7 lists past clusters.
Case nodeid, region, onset, reported_at, sku (optional)One sick person in the cluster. No names, no health data beyond onset date.

Seed: six cases in four states, five with a product named and one store-only. Every case store received an affected product lot before the purchase date. Two of the six stores also received the L-117 blend, so L-117 partially explains; none received anything from L-205, so the decoy explains nothing. The generator writes the expected ranking into data/expected.json and a test asserts it.

The tool: find_common_source

Input: a list of case ids. Output: every ingredient lot that could have reached each case, ranked. The rule is simple enough to say out loud: first the lot that explains the most cases, then the one that reached the fewest stores. The agent reads the table and writes the explanation; it computes nothing.

// For each case, walk back from the store to every ingredient lot that could have reached it,
// through product lots delivered before the purchase, batches, and rework (0..3 hops).
MATCH (c:Case) WHERE c.id IN $cases
MATCH (c)-[b:BOUGHT_AT]->(st:Store)<-[s:SHIPPED_TO]-(pl:ProductLot)
      <-[:PRODUCED]-(:Batch)<-[:REWORKED_INTO*0..3]-(:Batch)<-[:USED_IN]-(l:Lot)
WHERE s.shipped_at <= b.date AND (c.sku IS NULL OR pl.sku = c.sku)
WITH l, collect(DISTINCT c.id) AS explained
// How far did that lot spread in total? Fewer stores for the same cases = more specific.
MATCH (l)-[:USED_IN|REWORKED_INTO|PRODUCED|SHIPPED_TO*1..8]->(reach:Store)
WITH l, explained, count(DISTINCT reach) AS stores_reached
RETURN l.code AS lot, l.ingredient AS ingredient, l.supplier_id AS supplier,
       size(explained) AS cases_explained, explained,
       stores_reached, toFloat(size(explained)) / stores_reached AS specificity
ORDER BY cases_explained DESC, specificity DESC
LIMIT 10

A second tool, case_path, returns the backward path for one case (same pattern with path = and the case id as a parameter) for the evidence panel. The handler adds total_cases so the UI prints "6 of 6".

Agent behaviour

  • Outbreak mode has its own short prompt: call find_common_source once with all case ids, then write at most four sentences: the leading lot and how many cases it explains, the runner-up and why it does not explain the rest, the decoy ruled out, and the recommendation. It must say "likely" and that the coordinator and the supplier's test decide.
  • If no lot explains every case, say so and name the two leading lots. Never invent a lot.
  • The result is a proposal. The coordinator's click on Open incident is the decision, and it enters the seven-step recall flow unchanged.

Why the decoy matters on stage. L-205 is the same ingredient from the same supplier, received the same week. A keyword search or a spreadsheet filter would pull it in. The graph rules it out in one query because no path connects it to any case store. Say this in the video.

Live tracing

Judges score "explainable results" on what they can see in thirty seconds. The live trace is where they see it. It must make FalkorDB visibly the thing doing the work.

Event stream

  • SSE events: start, note (the agent's one-line intent), tool_start, tool_end (tool, input, one-line result, total ms, FalkorDB ms, Cypher list), done, error.
  • The graph route tags every node and edge with the step that reveals it and its hop count, so the network animates in the same order as the log.
  • Replay serves a recorded run as the same events with recorded delays; ?speed=2 halves the waits.

What each step card shows

  • Plain title, the agent's note, the one-line result.
  • Tool name and condensed input ("notices: 33 items").
  • FalkorDB latency badge per query; a running total in the header ("graph answered 9 queries in 31 ms").
  • Expanders: Cypher with parameters highlighted; query plan from GRAPH.EXPLAIN showing the index scan.
  • Decision cards for the hazard proposal and the gap policy, with the policy text and "awaiting the coordinator".

Path 1 · Seeded generator P0

  • build(seed) is pure: same seed, same graph. Planted cases are hard-coded and documented (bad lot L-204, blend with L-117 in B-03, rework B-03 to B-09, decoy L-205 in B-04 and B-06, two gap stores on P-02, four untouched stores, six outbreak cases in cluster OB-2026-10). Everything else is random from the seed.
  • load(data, reset) deletes the graph when asked, creates indexes, then loads each node and edge type with one UNWIND $rows query per type, in batches of 1,000 rows.
  • Writes data/expected.json: counts, store sets, units, held quantities, outbreak ranking. The tests assert the graph against it.
  • --scale N multiplies the random fill (stores, lots, batches, deliveries) while keeping the planted story at the centre, so answers stay 33 and 38 on a graph 50 times larger. Used for one benchmark line in the README. P1

Path 2 · FSMA 204 sortable spreadsheet import P1

The FDA's rule requires firms to produce a sortable spreadsheet of Key Data Elements within 24 hours. Most firms already keep this format. POST /ingest/fsma accepts the three tabs as CSV and builds the graph from them. This is the sentence for the pitch: "upload the spreadsheet the FDA already makes you keep, and the graph builds itself."

  • MERGE on identifiers everywhere, so re-uploading the same file is idempotent and a corrected file updates in place.
  • Dates are normalised to ISO; quantities to integers; units to kilograms or units by the Unit column.

Path 3 · Outbreak cases P0

  • POST /ingest/cases with CSV or tab-separated text: case_id, state, onset, store_id or store name, purchase_date, sku or product name (optional). Also the Paste box on Page 1.
  • Stores are matched by id, then by name and city; unmatched rows are returned with the reason and excluded, never guessed.
  • Writes Cluster, Case, HAS_CASE, BOUGHT_AT. Re-pasting the same cluster id replaces its cases.

Path 4 · openFDA enrichment P2

  • One scheduled pull from /food/enforcement.json fills the hazard select on Page 2 with the most frequent recall reasons and classes, and a "recent recalls like this" line in the hazard assessment (attributed, read-only, no firm data stored in our graph).

Rules for every path

  • Indexes exist before any load: Lot.code, Batch.id, ProductLot.id, Product.sku, Store.id, Supplier.id, Site.id, DC.id, Incident.lot, Case.id, Cluster.id.
  • Edges point forward in time, so the graph has no cycles and bounded variable-length matches are safe. The validation step checks it.
  • Invariants checked after load and reported: units made = shipped + held for every product lot; every case store received an affected lot before the purchase date; node and edge counts.
  • Loading is parameterised Cypher only; no string-built queries. Every loader query is in src/graph/queries.ts and quoted in the README.

Working rules

  • One owner per file. To change a file in another lane, open a small pull request and tag its owner. The files that cause most conflicts are App.tsx, styles.css, src/tools/index.ts and src/graph/queries.ts. After Dev C's split, styles.css gets one section per lane, marked with a comment.

  • Fixtures first. Frontend work starts from the fixture, never from waiting. The fixture is deleted only when the real route returns the same shape.
  • One FalkorDB per developer. Everyone runs the Docker container locally with the same seed, so tests and screenshots match. The hosted FalkorDB Cloud graph is for the demo only.
  • Demo path first. If an item is late at Sync 1, its owner says so then, and the lane with slack picks up the next item on the critical path.

Judging checklist, Track 1

  • Multi-hop reasoning. Forward trace through blend, rework, production and delivery; backward verification; outbreak traceback across six cases. Say the hop counts out loud: "eight hops, one query".
  • Graph queries and algorithms as agent tools. Ten Cypher-backed tools; SPpaths and BFS in the drawer and the reveal. Every tool's Cypher is visible in the UI and the README.
  • Tool selection through MCP. The agent discovers tools from our MCP server at runtime; the same server runs in Claude Code and Claude Desktop through .mcp.json.
  • Actions based on what the graph shows. Hold placed on inventory edges, class proposed, notices drafted, cluster recorded. The graph is written, not just read.
  • Explainable results. One plain sentence per store, the chain of records, the query, the latency, the decision cards, and a human confirm on every judgement.
  • Runs for the judges. Public URL with replay, repo with one-command Docker, video under three minutes.
  • Honest scope. Limits section in the README; "synthetic demo data" in the shell.

Risks and fallbacks

RiskFallback

The model skips a step or sends an array as a stringFixed step order in the prompt, list arguments accept JSON strings, the final JSON is built from tool output, not from the model.

Hosting the graph costs timeDocker Compose on a single VM is the fallback; FalkorDB Cloud is preferred for the sponsor story.
