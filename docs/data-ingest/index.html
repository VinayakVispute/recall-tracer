1. What we built

Dev A: graph and data

  • FalkorDB graph recall, one-to-one with FDA FSMA 204 traceability events.
  • Seeded generator: supplier → lot → batch → product lot → store, plus plants, DCs, rework and untracked shipments.
  • Seed 42 gives 170 nodes and 439 edges, the same every time.
  • Answer key in data/expected.json. For L-204 that is 31 affected stores, 2 coverage gaps and 2,256 units to pull.
  • A6 case ingest. Paste CSV or a spreadsheet table into an outbreak cluster. Bad rows come back with reasons.

Dev B: agent, MCP, API

  • MCP server with 10 graph tools: trace forward and back, coverage gaps, minimal recall, hold, classification, notice draft, common source and case path.
  • Recall agent with a live trace over SSE. Every tool call carries FalkorDB time and the Cypher it ran.
  • B2 replay. A recorded run streams back without a key or a database.
  • B4 outbreak mode. Cases to common source lot, ranked by how many cases each lot explains.
  • B5 incidents. History with minutes to scope and notice status.

2. Data sources

The demo data is synthetic. Real lot-level supply chain records (which lot went into which batch and shipped to which store) are private to each company and not published anywhere. So we generate a realistic network with a fixed seed, which also makes every demo run give the same, checkable answer.

Its shape and fields come from these public sources:

SourceWhat we take from it
FDA FSMA 204 Food Traceability RuleKey Data Elements and Critical Tracking Events (receive, transform, ship). These define our supplier → lot → batch → product lot → store chain.
openFDA Food Enforcement API
api.fda.gov/food/enforcement.json		Real recall records: recalling firm, reason, classification (Class I, II, III), distribution pattern. This is the shape of our classification and notice drafts.
USDA FSIS recallsThe same for meat and poultry recalls.
CDC foodborne outbreak investigationsCase counts, illness onset dates and states. This is the shape of our case rows.

To plug in real data later, map a company's traceability export onto the graph schema below. Cases from a health department line list go through the case ingest as they are.

3. Graph schema (FalkorDB)

(Supplier)-[:SUPPLIED]->(Lot)-[:USED_IN {qty_kg}]->(Batch)-[:PRODUCED {units}]->(ProductLot)-[:SHIPPED_TO {units, shipped_at}]->(Store) (Batch)-[:REWORKED_INTO {qty_kg}]->(Batch) (ProductLot)-[:OF]->(Product) (Lot)-[:STORED_AT {qty_kg}]->(Site) (ProductLot)-[:HELD_AT {units}]->(Site | DC) (Product)-[:SHIPPED_UNTRACKED {units, shipped_at}]->(Store) untracked shipments become coverage gaps (Cluster)-[:HAS_CASE]->(Case)-[:BOUGHT_AT {date}]->(Store) outbreak cases, loaded by case ingest (Incident)-[:CONCERNS]->(Lot)

Supplierid (S-03)name
Lotcode (L-204)ingredient, received_at, received_kg, supplier_id
Batchid (B-03)produced_at, site, site_id
ProductLotid (TLC-03A)sku, produced_at, best_by
Productsku (P-02)name, upc
Storeid (ST-029)name, city, region
Site, DCid (PL-1, DC-01)name, city, region

Why this schema

ChoiceReason
A graph (FalkorDB), not tablesA recall is a path question: which stores did this lot reach, and which lots reached these sick people. In a graph that is one traversal query. In SQL it is a chain of joins whose depth changes with rework.
Nodes follow FSMA 204 tracking eventsReceive, transform and ship are the events the FDA rule makes companies record. Because the graph uses the same shape, a real traceability export can be mapped in without redesigning anything.
Lot and ProductLot are separateA Lot is a raw ingredient from a supplier. A ProductLot is the finished, coded product on the shelf. Contamination enters at the ingredient, but stores pull product lots, so we need both and the link between them.
REWORKED_INTO between batchesLeftover batch gets mixed into a later batch. This is a real way contamination spreads that simple one-hop tracing misses.
Quantities on edges (qty_kg, units)The amount belongs to the movement, not to the thing. That is what lets us say "2,256 units to pull" instead of only listing stores.
SHIPPED_UNTRACKEDSome shipments have no lot code. We keep them as their own edge so they show up as coverage gaps instead of silently disappearing from the recall.
HELD_AT plants and DCsStock that hasn't reached stores yet must be put on hold, not pulled from shelves. It needs its own place in the graph.
Case and Cluster nodesA case is a person, not a shipment. BOUGHT_AT with a date ties them to a store, so outbreak mode can walk back from people to the common lot. A cluster groups cases of one pathogen.
sku is optional on a caseSick people often don't remember the exact product. A store and a date are enough to trace.
Case ids are globalThe same person must not be counted twice in two clusters, so a reused id is rejected instead of moved.
Incident node linked to the LotIt keeps history: minutes to scope, and the agent's proposed class kept apart from the human-confirmed class, for audit.
Dates as YYYY-MM-DD textThey sort and compare correctly as plain strings, with no timezone surprises.
Ingest by CSV or pasteHealth department case lists live in spreadsheets. Pasting rows is the shortest path. Parsing involves no AI, so it is fast, free and repeatable. Bad rows are reported with reasons rather than dropped.
Synthetic, seeded dataReal lot-to-store data is private. A fixed seed gives a known answer key, so tests and the demo can prove the agent got it right.

Same idea, different industry: a defective phone battery

In 2016 the Samsung Galaxy Note 7 had batteries from outside suppliers that could overheat and catch fire. Samsung first recalled about 2.5 million phones and put in batteries from another supplier. Those failed too, and the whole model was pulled. (Figures from public reporting, quoted from memory.) A recall like that has exactly the same shape as a food recall.

Our graphFoodPhone battery
SupplierFarm selling carrotsBattery maker
LotOne delivery of carrotsOne production lot of battery cells
BatchSoup cooked with those carrotsFactory run that put those cells into phones
ProductLotCoded cans of soupFinished phones with serial numbers
Site, DCPlant and warehouseFactory and regional warehouse
StoreSupermarketPhone shop or carrier store
CaseA person who got sickA customer whose phone caught fire
ClusterOne outbreakAll fire reports for one defect
IncidentOur recall recordThe maker's recall record

How one bad part spreads, and the part of the schema that catches each step:

  1. Bad part at the start. One lot of battery cells is faulty. That is a Lot linked by SUPPLIED to its Supplier.
  2. It fans out. One cell lot goes into many factory runs, and each run makes thousands of phones (USED_IN, then PRODUCED). "Which shops got phones with cells from lot X?" is one path query in a graph.
  3. Ingredient vs finished product. Shops don't pull battery lots, they pull phones by serial number. That is why Lot and ProductLot are separate.
  4. Quantities. "Pull 4,000 phones from these 30 shops" beats "pull everything". The counts live on the links (units, qty_kg).
  5. Rework. Repaired or refurbished phones go back into stock. That is REWORKED_INTO, the path simple tracing misses.
  6. Still in the warehouse. Phones not yet in shops are stopped at the warehouse. That is HELD_AT a Site or DC.
  7. Missing records. Shipments with no serials recorded are kept as SHIPPED_UNTRACKED, so they show up as coverage gaps instead of vanishing.

Working backwards is outbreak mode. Fire reports come in from different cities. Each is a Case linked to the shop it was bought at (BOUGHT_AT). We walk back from every case to the one battery lot they all share. That is find_common_source.

The second failure is why we name decoys. Changing supplier didn't fix the Note 7, because the new batteries had their own flaw. Our outbreak summary also names lots from the same supplier and ingredient that do not explain the cases, so nobody blames or clears the wrong lot by guesswork.

Why this shows the schema is right. Food and electronics recalls share one shape: a part from a supplier goes into products, and products ship to shops and reach people. Both record the same three events (receive, make, ship), and our nodes and links are exactly those events. The same graph and queries work for a carrot or a phone battery.

4. Case ingest schema

One case is one sick person: where and when they bought the food, and when they got ill. Paste CSV, or copy rows straight from a spreadsheet (tab separated). A header row is optional.

Columns

ColumnRequiredFormatExampleRule
idyes1 to 40 letters, digits or dashesC1Unique across all clusters. Twice in one paste is rejected.
regionyestextOHNot empty.
onsetyesYYYY-MM-DD2026-10-12Not before bought_at.
reported_atyesYYYY-MM-DD2026-10-13Not before onset.
skunoproduct skuP-02Empty means the product is unknown.
storeyesstore id, or store name with cityST-029Must match a store in the graph. Case does not matter.
bought_atyesYYYY-MM-DD2026-10-11The purchase date.
citynotextClevelandHeader mode only. Lets store be a name like FreshMart #029.

Without a header, columns are read in the order above (without city). With a header whose first cell is id, columns are matched by name in any order.

Request

POST /ingest/cases
Content-Type: application/json

{
  "cluster": "OB-2026-10",              // 1-40 letters, digits or dashes
  "pathogen": "Listeria monocytogenes", // required only when the cluster is new
  "text": "id\tregion\tonset\t..."      // the pasted CSV or tab text
}

Response (200)

{
  "cluster": "OB-2026-10",
  "created": false,        // true when this call opened the cluster
  "loaded": 5,             // cases written
  "rejected": [            // bad rows, nothing is dropped silently
    { "row": 7, "line": "C9,OH,2026-10-01,...", "reason": "onset is before the purchase date" }
  ]
}

Rejected rows are data, not an error, so the UI can show "row 7 rejected" next to the paste. Errors (400) are only a bad cluster id, an empty paste, or a new cluster with no pathogen.

Rejection reasons

  • case id must be 1-40 letters, digits or dashes
  • case C1 appears twice in this paste
  • region is empty
  • onset / reported_at / bought_at must be a date like 2026-10-09
  • onset is before the purchase date
  • reported_at is before onset
  • no store matches "X" in City
  • case C1 already belongs to cluster OB-2026-09

Behaviour

  • Idempotent. Pasting the same rows twice changes nothing.
  • Additive. Cases already in the cluster but missing from a new paste stay.
  • Corrections replace. Re-pasting a case with a new store or date updates it and moves its purchase link.
  • No Claude call. Ingest is plain parsing and Cypher, so it works without an API key.

5. Try it

# load cases
curl -X POST localhost:8787/ingest/cases -H 'content-type: application/json' \
  -d '{"cluster":"OB-2026-10","text":"C1,OH,2026-10-12,2026-10-13,P-02,ST-029,2026-10-11"}'

# find the common source (top answer: L-204 explains 6 of 6 cases)
curl -N 'localhost:8787/outbreak/stream?cluster=OB-2026-10'

# replay the recorded L-204 recall, no key needed
curl -N 'localhost:8787/recall/replay?lot=L-204&speed=10'

Hosts are local for now. The live app URL comes after deploy.
